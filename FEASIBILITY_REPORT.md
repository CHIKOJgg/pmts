# FEASIBILITY_REPORT — реальная эксплуатация PMTS

Дата: 2026-08-19. Статус репозитория: pytest passing (run `pytest` to see the current test count; the suite must pass before live trading), mypy strict green (71 файлов),
ruff check green. Бэктест 2000 тиков: P&L −0.77%, Sharpe −280 (см. §4).

---

## 1. Вердикт

**Бот не готов к live-капиталу в текущем виде.** Инфраструктура (риск, мониторинг,
dashboard, kill switch, reconciliation, хранение) — зрелая и рабочая; торговая модель
(кросс-вендорный арбитраж + дельта-нейтральный MM) — нет: она не проверена против
реальных рынков и структурно убыточна в честной симуляции филлов.

Минимально жизнеспособный сценарий — **paper-торговля на реальных фидах 2–4 недели,
затем микро-реальный режим на 1–2 зеркальных событиях с лимитом $50/ордер**, и только
потом арбитраж с ножками на обеих площадках.

## 3. Блокеры и риски реализуемости

### 3.1. Совпадение событий PM ↔ Opinion — главный экзистенциальный риск
- Арбитраж легален только между **идентичными событиями с идентичным критерием
  резолюции**. Рынки двух площадок почти никогда не совпадают 1:1; код требует
  ручного `market_registry` (логический market → venue-id) в конфиге
  (`config/settings.py`, `main.py:_venue_market_ids`), реестра синхронизации событий
  **нет**.
- Даже «похожие» события могут резолвиться по разным источникам → одна ножка
  выигрывает, вторая нет. **Это не арбитраж, а ставка на корреляцию резолюций** —
  риск не хеджируется парами ножек.
- Действие: до live-арбитража — вести таблицу реальных зеркальных событий обеих
  площадок вручную, проверять текст правил резолюции дословно, стартовать с 1–2
  событий.

### 3.2. Микро-ликвидность Opinion
- Opinion — низколиквидная площадка: стакан из нескольких ордеров, широкие спреды.
- Средний slippage в бэктесте — 33.7 bps при лимите ордера $200; на реальном Opinion
  стакан $100–200 может отсутствовать вовсе → ордер повиснет или прольётся по худшей
  цене. `max_single_order_usdc=200` — потолок, а не ориентир.
- Действие: уменьшить ордера до $25–50 на Opinion, обязательный лимит
  `min_depth`-проверки перед отправкой (сейчас только `estimate_taker_cost` для
  эвристик), отдельный fail-closed по глубине Opinion.

### 3.3. Комиссии 20/25 bps и порог прибыльности арбитража
- PM taker 20 bps (`PM_TAKER_FEE_BPS=20`), Opinion 25 bps (`OP_TAKER_FEE_BPS=25`).
- Пара ножек стоит **≥ 45 bps** только комиссий + двусторонний спред. `min_net_edge`
  по умолчанию 0.003 (30 bps) **ниже безубытка** — реальный порог должен быть
  ≥ 60–70 bps с учётом проскальзывания.
- Действие: пересчитать `min_net_edge` под реальные котировки (формула: fees +
  half-spread_1 + half-spread_2 + запас).

### 3.4. MM-шорты → расхождение бэктеста и live (NegativeHoldings)
- В бэктесте филл, приводящий к отрицательному остатку, **пропускается**
  (`backtest/engine.py` NegativeHoldings-скипы) → MM-позиции в симуляции ведут себя
  иначе, чем в реальности.
- В live `PortfolioManager` **разрешает** `SELL_YES`/`SELL_NO` сверх остатка только
  как ошибку (guard в `portfolio/manager.py:124-148`) — т.е. реальный MM-шорт
  упрётся в отказ или потребует протокола шортов (майнинг/займ), которого в коде нет.
- Действие: решить судьбу MM-шортов явно: либо запретить продажи без инвентаря
  (live = бэктест), либо внедрить шорт-протокол и убрать guard-расхождение.

### 3.5. On-chain redeem: только YES-нога
- Резолюция в коде: `MarketMonitor`/`ResolutionMonitor` опрашивают резолюцию,
  `PolymarketClient.redeem_market` — on-chain CTF-redeem (только YES-токены:
  `_settle_positions` в `engine/orchestrator.py`, `RedemptionRecord`).
- **NO-токены после резолюции не редимятся** → если бот держит NO, они застревают
  (нужно продать до резолюции или дописать NO-redeem + газ).
- Opinion: redeem через `ctf_exchange_addr` — те же ограничения + нужен POL для газа.
- Действие: перед live — дописать redeem обеих ног и мониторинг резолюций с
  алертом «позиция не продана до резолюции».

### 3.6. Исполнение
- Бэктест заполняет ордера только при кросс-условии — честно, но это значит, что
  активный MM структурно платит спред (см. §4). В live: частичные филлы, время
  жизни ордера, nonce-очереди и rate-limit CLOB — `ExecutionEngine` это учитывает
  (tracker, retry, reconciliation), но **ни разу не проверено против боевого API**.
- Действие: сначала прогнать `verify_connectivity`/sandbox на реальных ключах,
  затем paper на реальных фидах (`--mode paper` с WS/REST-адаптерами), затем
  live на минимальных суммах.

### 3.7. Операционные
- Kill switch + алерты + dashboard — есть и работают; порты: dashboard по умолчанию
  на observability-порту (не забыть `OBSERVABILITY_BIND_HOST` и защиту).
- `max_mtm_age_ms` fail-closed работает (тест stale-фида в `test_integration.py`).
- Нет: системного мониторинга бот-процесса (restart policy есть в Docker),
  ночного/праздничного расписания вне `TradingSchedule`, бэкапа state.
- Юридическое: PM — geo-restricted (US запрещён); Opinion — аналогично. Ответственность
  за соблюдение — на операторе; `compliance/trade_report.py` экспортирует CSV-отчёты
  для налоговых целей (пофикшен баг side/platform).

## 4. Количественная картина (из бэктеста 2000 тиков)

```
P&L:          $-76.88  (-0.77%)
Max DD:       0.90%
Sharpe:       -280.47
Fills:        319 full | 34 partial | 100% fill rate
Avg slippage: 33.7 bps
```

- **MM** (−0.77%): структурно убыточен при cross-only филлах — каждая сделка платит
  спред+комиссию, выигрыш инвентаря в бэктесте не компенсирует. Это честный результат
  модели, а не баг. Реальный MM имеет смысл только с maker-филлами и займом
  ликвидности — вне текущего скоупа.
- **Арбитраж** в синтетике прибылен только при внесённом смещении (`--pm-bias`):
  порог = fees + 2×half-spread. На реальных данных порог должен считаться
  от живых стаканов, иначе арб будет фильтроваться (это правильно).
- Вывод: бэктест пригоден как **регрессионный контракт**, но не как доказательство
  прибыльности. Доказательство — только paper на реальных фидах.

## 6. Обязательные доработки кода перед live (чек-лист)

1. `min_net_edge` — расчёт от живых стаканов (fees + спреды + запас), не константа.
2. Решить судьбу MM-шортов (запрет или протокол) — убрать расхождение с бэктестом.
3. NO-нога редимпинга + газ-мониторинг для on-chain redeem.
4. Глубинно-лимитированные ордера на Opinion (отказ при `depth < size×k`).
5. Прогон `--mode paper` на реальных фидах (WS-адаптеры) — сейчас paper использует
   только `PaperTradingClient` с синтетическим фидом.
6. Авто-реестр зеркальных событий (или ручная таблица с CI-проверкой резолюций).
7. Бэкап SQLite/Postgres state + алерт «бот не торговал N часов».
